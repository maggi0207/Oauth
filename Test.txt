Integrate RMA Skills and MCP Tools into the New Multi-Agent Architecture

We now need to implement the next phase of the new architecture.

Architecture Context

We have two existing repositories:

* Service Plan Main Agent: ssc-service-plan-agent-rt
* RMA Agent: existing RMA repository

The target architecture is:

User
 │
 ▼
Service Plan Main Agent
 │
 │ LangGraph routing
 ▼
RMA Sub-Agent
 │
 ├── RMA Skills (.md)
 │
 ├── Skill-specific instructions
 │
 └── Corresponding MCP Tool
 │
 ▼
MCP Server
 │
 ▼
RMA backend/system

The Service Plan Agent is the Main Agent / Orchestrator.

RMA should now operate as a sub-agent inside the Service Plan LangGraph workflow.

⸻

Objective

Integrate the existing RMA implementation into ssc-service-plan-agent-rt.

The RMA sub-agent must:

1. Use the existing RMA skill .md files.
2. Determine which RMA skill is applicable to the user request.
3. Load/use the corresponding skill instructions.
4. Identify the MCP operation required by that skill.
5. Invoke the corresponding MCP tool.
6. Return the MCP result back through the RMA sub-agent.
7. Pass the result back to the Service Plan Main Agent through LangGraph state.
8. Allow the Main Agent to generate the final response.

Do not duplicate the existing RMA skill definitions unnecessarily.

⸻

Step 1 — Analyze Existing RMA Skills

First inspect the existing RMA repository and identify all available .md skill files.

For every skill, determine:

Skill Name
Skill Description
Trigger / Intent
Required Parameters
MCP Tool
MCP Operation
Expected Input
Expected Output
Dependencies

Create an internal mapping such as:

RMA Skill
   ↓
Skill Instructions (.md)
   ↓
Intent / Trigger
   ↓
MCP Tool
   ↓
MCP Operation

Do not assume the mapping.

Derive it from the existing source code, skill files, configuration, and MCP integration.

⸻

Step 2 — MCP Path

The MCP path/tool information will be provided by Bruno.

Use the MCP path supplied by Bruno as the source of truth.

For example, if Bruno provides something conceptually like:

<BRUNO_PROVIDED_MCP_PATH>

use that exact MCP path/tool configuration.

Important

Do NOT:

* invent an MCP path
* hardcode a guessed MCP endpoint
* create duplicate MCP tools
* change the MCP contract without justification
* assume tool names based only on the skill name

If the MCP path from Bruno is not available in the repository/context, clearly identify it as a required integration input instead of guessing.

⸻

Create/refactor the RMA implementation so that the RMA sub-agent follows this flow:

      │

      ▼

The .md files should remain the source of truth for skill-specific behavior/instructions wherever the existing architecture already follows this approach.

Avoid duplicating the complete skill instructions into Python/TypeScript code.

⸻

Step 5 — MCP Tool Selection

The RMA sub-agent should not blindly call an MCP tool.

The flow should determine:

User Request
    ↓
RMA Intent
    ↓
Matching Skill
    ↓
Required MCP Operation
    ↓
MCP Tool

For example:

User Request
    ↓
RMA Skill A
    ↓
MCP Operation A
    ↓
Bruno MCP Path A

and:

User Request
    ↓
RMA Skill B
    ↓
MCP Operation B
    ↓
Bruno MCP Path B

The implementation must be extensible so that adding a new RMA skill does not require rewriting the Main Agent.

⸻

Step 6 — Keep Main Agent Generic

The Service Plan Main Agent should NOT contain logic such as:

if RMA request:
    call specific RMA MCP tool

Instead, it should only be responsible for routing to the RMA sub-agent.

Conceptually:

Main Agent
   │
   ├── RMA → RMA Sub-Agent
   ├── Future Agent A → Future Sub-Agent A
   ├── Future Agent B → Future Sub-Agent B
   └── ...

RMA-specific skill selection and MCP invocation must remain inside the RMA sub-agent boundary.

⸻

Critical Constraints

1. Do not rewrite the existing RMA business logic unnecessarily.
2. Do not duplicate skill .md content into code unless required by the existing architecture.
3. Do not guess MCP paths. Use the path provided by Bruno.
4. Do not put RMA-specific MCP logic inside the Main Agent.
5. Do not tightly couple the Main Agent to individual RMA skills.
6. Use LangGraph as the orchestration mechanism.
7. Keep the RMA implementation modular as a sub-agent/subgraph.
8. Design the architecture so additional sub-agents can be added later.
9. Preserve existing RMA functionality.
10. Follow existing coding patterns before introducing new abstractions.
