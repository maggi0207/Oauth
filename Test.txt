# FOREP-2703 — Implement Active IPR DELETE API in FACTS API

Act as a senior .NET engineer. Implement the DELETE API for Active IPR by following the existing FACTS API coding patterns and repository instructions exactly.

## Objective

Implement a secure API that allows only a Lead Chemist to delete an Active IPR that was created in error, provided that the Active IPR is not currently in use.

Jira requirement:
- Ticket: FOREP-2703
- API area: `/api/ActiveReaction`
- Requirement: Delete an Active IPR created in error.
- If the Active IPR is in use, return an appropriate error and do not delete it.

**Implement and verify the backend API first. Do not implement the Angular UI in this task.**

## Phase 1 — Inspect the repository and existing patterns

Before changing code:

1. Read the applicable repository instructions and installed coding skills.
2. Inspect the existing implementation of:
   - `ActiveReactionController.cs`
   - `ActiveReactionService.cs` and its interface
   - Existing GET/PUT/POST ActiveReaction endpoints
   - The corresponding data-access/repository layer
   - `ApplicationDbContext` or equivalent EF configuration
   - Existing authorization attributes, permission matrix, and role checks
   - Existing exception handling and `ProblemDetails` responses
   - Existing tests for ActiveReaction and similar DELETE endpoints
3. Identify how the application determines whether an Active IPR is being used by an active formulation.
4. Identify the existing database deletion method and relationship constraints.
5. Inspect the current DEV Swagger specification and the existing route conventions.

Do not introduce a new architecture, repository abstraction, authorization mechanism, or exception-handling pattern when an existing pattern can be reused.

## Phase 2 — Confirm the endpoint contract

Existing API conventions include:
- `/api/ActiveReaction`
- `/api/ActiveReaction/{activeIprId}`
- `/api/ActiveReaction/search`

The ticket text mentions `DELETE /api/ActiveReaction`, but does not specify the identifier parameter.

Follow the existing RESTful route convention and implement:

`DELETE /api/ActiveReaction/{activeIprId}`

Use the same identifier type as the existing ActiveReaction GET/PUT endpoints.

Do not implement a separate `/Delete` route unless repository conventions or an explicit requirement establish that route.

Document the route and expected responses in Swagger/OpenAPI.

## Phase 3 — Authorization

Only a Lead Chemist may delete an Active IPR.

1. Reuse the existing role/permission infrastructure.
2. Enforce authorization on the API endpoint, not only in the UI.
3. Follow the existing permission-matrix conventions.
4. Ensure unauthorized users cannot delete records by calling the endpoint directly.
5. Do not introduce a new authentication or role-management mechanism.

Verify the authorization behavior using existing test patterns.

## Phase 4 — Deletion and in-use validation

Implement the deletion through the existing service and data-access patterns.

Before deleting:

1. Verify the Active IPR exists.
2. Check the actual application/database relationships that determine whether it is in use.
3. If it is in use, reject the deletion and preserve the record.
4. If it is not in use, delete it using the established persistence mechanism.
5. Handle missing identifiers/records using the project's established API conventions.

Important:
- Do not guess which database table or relationship determines whether an Active IPR is in use.
- Inspect the existing schema and domain logic.
- Do not delete related records as a workaround.
- Do not bypass foreign-key constraints.
- Avoid a check-then-delete race where feasible; use the existing transaction/concurrency pattern if available.

## Phase 5 — HTTP responses and errors

Follow existing FACTS API conventions and Swagger response documentation.

Cover:
- Successful deletion
- Record not found
- User lacking permission
- Record currently in use
- Unexpected database/service failure

Use the repository's existing exception and `ProblemDetails` handling. Preserve meaningful status codes and error messages.

Do not return success when deletion has failed.

## Phase 6 — Tests

Add focused unit/integration tests following the existing test framework and fixtures.

At minimum, test:

1. Existing, unused Active IPR can be deleted by a Lead Chemist.
2. Deleted record is no longer retrievable.
3. Missing Active IPR returns the established not-found response.
4. Active IPR in use cannot be deleted.
5. A failed deletion leaves the record intact.
6. A non-Lead-Chemist cannot delete the record.
7. Other existing ActiveReaction GET/PUT/POST/search behavior remains unchanged.

Use realistic fixtures and the actual persistence/query patterns. Do not weaken or remove existing tests to make the new tests pass.

1. Build the FACTS API.

3. Start the API with the repository's normal local configuration.
4. Confirm the DELETE endpoint appears in Swagger.
