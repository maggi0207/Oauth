# SDI FORECAST AGENT — PRODUCTION INTEGRATION

The standalone SDI Forecast Routing Agent is now working correctly.

It supports:
- Forecast Outlook
- Forecast Accuracy
- PID
- Product Family
- Business Unit (BU)
- Product Life Cycle
- LLM-based intent classification and routing
- Skill selection
- MCP tool execution
- Response synthesis

Now migrate this working implementation into our existing SDI
application architecture.

The objective is to replace the standalone CLI workflow with
an interactive chatbot integrated into our existing UI.

IMPORTANT:
Do not rebuild the agent from scratch.
Do not lose any working functionality.
Reuse the existing CLI implementation as the functional reference.

==================================================
3. RESPONSIBILITY OF EACH REPOSITORY
==================================================

A. RUNTIME AGENT

The Runtime Agent must own all agent-related logic.

Move or integrate the working CLI agent logic into this repository.

It must handle:

- LLM client initialization
- Configurable LLM model selection
- Conversation state
- Intent classification
- Skill selection
- Skill execution
- MCP tool selection
- MCP execution
- MCP response processing
- Response synthesis
- Error handling
- Retry handling, where appropriate
- Streaming responses, if supported by the existing architecture

The Runtime Agent must be the single source of truth for
agent orchestration and reasoning.

Do not duplicate this logic in the backend service or UI.

B. BACKEND SERVICE

The backend service must act as the proxy/API layer between
the Angular UI and the Runtime Agent.

It must handle:

- UI-facing API endpoints
- Forwarding chat requests to the Runtime Agent
- Forwarding streaming responses to the UI
- Authentication and authorization, following existing patterns
- Request validation
- Correlation/request IDs
- Error propagation
- Appropriate logging
- Timeouts and connection handling

Do not implement LLM reasoning, skill selection, or MCP
orchestration in this service.

Do not make the UI call the Runtime Agent directly if the
existing architecture requires the service as the proxy.

C. ANGULAR UI

Integrate an interactive chatbot into the existing SDI UI.

Reuse the existing UI components, design system, styling,
routing, and coding patterns.

Do not create an unrelated standalone frontend.

==================================================
7. INTERACTIVE CHATBOT
==================================================

The UI must provide an interactive chatbot.

Users should be able to:

- Enter natural-language questions
- Send messages
- See their messages and agent responses
- Continue asking follow-up questions
- Maintain conversation context
- See loading and processing states
- See errors in a user-friendly way
- Start a new conversation
- View previous messages in the current conversation

Example conversation:

User:
Show me the forecast for PID ABC123.

Agent:
Here is the forecast outlook for PID ABC123...

User:
What about forecast accuracy?

Agent:
Here is the forecast accuracy for PID ABC123...

The second question should reuse the PID from the conversation
when the context makes that interpretation unambiguous.

If the question is ambiguous or missing required information,
the agent should ask the user for clarification.

Do not fabricate forecast values.

==================================================
8. STREAMING RESPONSES
==================================================

Inspect the existing Runtime Agent and service implementation
for streaming support.

If streaming is already supported, reuse it.

Otherwise, implement streaming using the existing project
patterns, preferably Server-Sent Events (SSE) if compatible.

Expected behavior:

1. User submits a message.
2. UI displays the user's message immediately.
3. UI shows an assistant response in progress.
4. Backend forwards the request to the Runtime Agent.
5. Runtime Agent processes the request.
6. The response is streamed through the service.
7. UI renders the response as it arrives.
8. UI marks the message as complete.

Ensure that errors and interrupted streams are handled.

Do not introduce WebSockets unless the existing architecture
requires them.
