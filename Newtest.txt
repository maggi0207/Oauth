Task: Implement Reference-Based Agent UI with Real-Time Execution Streaming and Animations

Objective

Use the attached UI reference image as the target design for the existing SDI Chat UI.

Implement a modern, minimal, animated agent experience that shows what the agent is actually doing while processing a request. The interface must display real execution stages, selected skill and procedure, parameter validation, actual MCP tool execution, result processing, and incremental answer generation.

The reference image defines the intended visual experience. The actual runtime events define what the UI is allowed to display.

Do not rebuild the backend architecture or change business logic. First inspect the current implementation, identify the existing event stream, and reuse it. Make only the changes necessary to deliver the experience.

1. Inspect the Current Implementation

Inspect the existing UI, service, and runtime streaming path:

* Angular chat container and assistant message components.
* Chat API service and SSE parser.
* Existing routing-workflow/activity component.
* Express BFF streaming endpoint.
* FastAPI service streaming proxy.
* Runtime progress event implementation.
* Orchestrator, skill selector, execution adapter, MCP invocation, and response generator.
* Existing loading stages, timers, animations, and response rendering.

Determine which stages already emit events, which events are being dropped or buffered, and which UI states are hardcoded.

Do not start by creating new progress stages before inspecting the existing event protocol.

2. Implement the Real-Time Activity Lifecycle

Use the following stages as the target user experience. Map them to existing backend events wherever possible.

Stage 1 — Request received

Immediately display a compact assistant activity indicator:

Thinking…

Once request acceptance is confirmed, show:

Request received

The initial indicator may represent a waiting/connecting state before the first event arrives, but it must not imply that the agent has already started a specific operation.

Stage 2 — Understanding the request

When actual request interpretation begins, display:

Understanding your request…

Optional explanatory text:

Identifying the relevant capability and required parameters.

Show a subtle animated ring or dots while this operation is genuinely in progress.

Do not invent separate LLM-thinking stages if the runtime does not expose them.

Stage 3 — Skill selection and validation

When the selection result arrives, display the actual skill and procedure:

✓ Skill selected
Forecast
Procedure: Outlook

Then show the real validation stages, when individually available:

✓ Request received
✓ Skill catalog reviewed
✓ Skill selected
✓ Parameters extracted
✓ Parameters validated
◌ Preparing execution…

The selected skill, procedure, and extracted parameters must come from the actual validated runtime result.

Do not show parameter values unless they are safe to display and necessary for understanding the request.

Stage 4 — MCP execution

When the approved tool call starts, make it the primary active operation:

◌ Retrieving forecast data…
Snowflake MCP
Tool: query_rma_forecast_rates
Status: Running

Use the actual tool and server metadata from the execution layer.

The timeline should reflect real events:

✓ Approved execution prepared
✓ Query validated
✓ MCP connection established
◌ Executing query…
◌ Receiving results…

Show only the stages the backend can verify. If connection setup is not separately instrumented, do not display it as an independent completed stage.

If the execution is an Install Base question-passthrough operation, describe the actual lookup instead of pretending that a SQL query was generated.

Stage 5 — Results and response generation

Once the MCP call returns, display its confirmed outcome:

✓ Forecast data retrieved
  45 rows · 1.8s

Use actual row counts and measured durations when available.

Then show:

✓ Results received
◌ Preparing your response…

The response-generation state must begin when the actual response-generation operation starts, not when a timer expires.

Stage 6 — Incremental answer streaming

Inspect whether the configured Response LLM supports native streaming.

If native streaming is supported, progressively render validated answer segments inside the same assistant message as they become available.

The desired experience is:

◌ Preparing your response…
The forecast outlook for ISR4451-X/K9 shows…
[More validated answer content appears progressively]

Requirements:

* Use actual LLM streaming, not simulated browser typing.
* Keep activity events separate from answer-content events.
* Do not create a new assistant message for each token or delta.
* Do not wait for the entire response if validated segments can safely be emitted earlier.
* Preserve existing response formatting, result tables, exports, and follow-up prompts.
* Prevent duplicated content when the final response arrives.
* Preserve the current grounding, sanitization, and security checks.

If the provider does not support native streaming, retain the genuine activity timeline and display the complete validated response when ready. Report this limitation honestly.

Stage 7 — Completed state

When the request actually completes, collapse the activity to a compact summary:

✓ Completed in 14.2s
View activity ▾

The duration must reflect the actual request lifecycle.

Keep the assistant answer visible below the summary.

The user must be able to expand the activity timeline to inspect the actual execution history.

Stage 8 — Failed state

If a real operation fails, show the failed stage and a concise, safe explanation.

Example:

⚠ Failed to retrieve forecast data
The data request could not be completed.
View details
Try again

A failed operation must never be marked completed. Retry must use the existing request-handling behavior and must not create duplicate MCP calls automatically.

3. Implement the Visual Design from the Reference

Use the attached reference as the visual guide.

The target should feel like a modern AI assistant, not an operational dashboard.

Default activity appearance

* Compact activity content embedded in the assistant message.
* Subtle animated active-operation indicator.
* Clear current-action label.
* Completed actions shown in subdued text.
* Skill and procedure metadata presented compactly.
* Actual MCP tool details displayed without overwhelming the conversation.
* Smooth transitions as real events arrive.
* A collapsed activity history after completion.

Animations

Implement restrained animations for:

* Initial thinking indicator.
* Active skill-selection or execution state.
* Active MCP call.
* New activity-line appearance.
* Transition from activity to streamed answer.
* Completed and failed states.

Animations must:

* Respond to actual state changes.
* Avoid unnecessary movement and layout shifts.
* Respect reduced-motion preferences.
* Stop on completion, cancellation, or failure.
* Avoid fake percentage progress.
* Avoid artificial delays intended to make the agent appear busy.

Remove the oversized dashboard-style card, unnecessary nested containers, excessive checkmarks, and hardcoded progress bars where they conflict with the reference.

4. Use One Real Event Stream

Reuse the current SSE connection and event protocol.

Inspect existing events such as:

agent, route, stage_start, stage_done, ping, complete, and error.

Add compatible events only where necessary for missing real operations or native response deltas.

Every event must be emitted at the corresponding real operation boundary.

The frontend must correctly handle:

* Multiple events within one network chunk.
* Events split across network chunks.
* Keepalive comments and pings.
* Delayed and duplicate events.
* Connection errors and cancellation.
* Response deltas followed by the final response.
* Correct association between events and their request/session IDs.

A missing backend event must not be fabricated in Angular.

6. Preserve Existing Functionality

This task is strictly for the real-time UI experience and the minimum supporting event changes.

Do not modify:

* Dynamic skill-selection business logic.
* Multi-skill routing or execution planning.
* SQL generation and validation.
* MCP tool selection or execution semantics.
* Redis checkpointing or conversation memory.
* LangGraph architecture.
* Authentication or authorization.
* Unrelated application pages.

Do not replace the current streaming architecture with a new implementation. Preserve the non-streaming API and existing chat features.

7. Tests and Live Validation

Test the activity lifecycle, including:

* Initial waiting state.
* Actual request-start event.
* Skill selection and parameter validation.
* MCP execution start and completion.
* Result processing.
* Response-generation start.
* Incremental answer deltas.
* Final completion without duplicate text.
* Failed MCP and LLM operations.
* Stream disconnect and cancellation.
* Duplicate and out-of-order events.
* Expanded/collapsed activity history.
* Reduced-motion accessibility.
* Existing tables, exports, and follow-up interactions.

Then run the actual development UI with the configured services.

Submit a real supported query and verify:

1. The activity appears immediately.
2. Real events update the active operation.
3. The selected skill and tool match the actual execution.
4. The MCP operation displays its real running and completion states.
5. The answer streams progressively if native streaming is supported.
6. The final answer appears exactly once.
7. The activity collapses into the completed state.
8. Failures are displayed honestly.
9. Existing chat behavior remains intact.

Mocks alone are insufficient to claim end-to-end success.

8. Final Report

Report:

* The original cause of missing or outdated progress.
* Existing events reused.
* New real events added, if any.
* UI components changed.
* Whether native response streaming works.
* Automated test results.
* Real development validation results.
* Remaining unsupported stages or blockers.

Do not claim that all stages stream in real time unless the actual runtime emits and the UI receives the corresponding events.
